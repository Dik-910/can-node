# 通信协议

> 状态：**草案 v0.1**。三方共用（can-node / bms-node / smartgateway），
> 任一侧修改报文定义必须同步更新本文件并提升版本号。

## 1. ID 分配

采用 11 位标准帧。按功能域分段，避免不同节点争用同一 ID：

| 区间 | 用途 | 说明 |
|---|---|---|
| `0x100` – `0x17F` | 节点状态 | 心跳、错误计数、版本 |
| `0x180` – `0x1FF` | 实时数据 | 采样值、周期上报 |
| `0x200` – `0x27F` | 控制命令 | 网关下发 |
| `0x280` – `0x2FF` | 事件与故障 | 故障码、状态迁移 |
| `0x7DF` | 诊断功能寻址 | 广播请求 |
| `0x7E0` – `0x7E7` | 诊断物理请求 | tester → ECU |
| `0x7E8` – `0x7EF` | 诊断物理响应 | ECU → tester |

约束：

- 同一 ID 只允许一个发送方，多节点需要同数据时由发送方广播。
- 周期报文抖动控制在 ±10% 内。
- 诊断报文不设周期，按需触发。

## 2. 报文定义

### 2.1 节点状态 `0x180`

发送方：can-node。周期 100 ms。DLC = 8。

| 起始位 | 长度 | 信号 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 8 | `node_state` | uint8 | 0 初始化 / 1 正常 / 2 降级 / 3 故障 |
| 8 | 8 | `err_level` | uint8 | 0 主动 / 1 被动 / 2 BusOff |
| 16 | 16 | `busoff_cnt` | uint16 | 累计 Bus Off 次数，小端 |
| 32 | 32 | `uptime_s` | uint32 | 上电秒数，小端 |

### 2.2 总线状态 `0x181`

发送方：can-node。周期 20 ms。DLC = 8。

| 起始位 | 长度 | 信号 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 8 | `tec` | uint8 | 发送错误计数，0–255 |
| 8 | 8 | `rec` | uint8 | 接收错误计数，0–255 |
| 16 | 16 | `bus_load_pm` | uint16 | 总线负载率，千分比 |

> TEC 在 Bus Off 判据中需要超过 255，单字节装不下。本表按饱和值 255 上报，
> 真实的超限由 UDS `0x22` 按 DID 读取 2 字节原始值。

### 2.3 采样数据 `0x200`

发送方：bms-node。周期 50 ms。DLC = 8。

| 起始位 | 长度 | 信号 | 类型 | 因子 / 偏移 | 单位 |
|---|---|---|---|---|---|
| 0 | 16 | `pack_voltage` | uint16 | ×0.01 | V |
| 16 | 16 | `pack_current` | int16 | ×0.01，充电为正 | A |
| 32 | 8 | `soc` | uint8 | ×1 | % |
| 40 | 8 | `temp_max` | int8 | ×1，偏移 −40 | ℃ |
| 48 | 8 | `prot_state` | uint8 | 0 正常 / 1 告警 / 2 保护 / 3 恢复 | — |
| 56 | 8 | `fault_code` | uint8 | 当前最高优先级故障码，0 表示无 | — |

### 2.4 控制命令 `0x300`

发送方：网关。事件触发，非周期。DLC = 4。

| 起始位 | 长度 | 信号 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 8 | `cmd` | uint8 | 1 启动 / 2 停止 / 3 清故障 |
| 8 | 8 | `seq` | uint8 | 序列号，回滚重发用 |
| 16 | 16 | `param` | uint16 | 命令参数，保留 |

> 带 `seq` 是因为 CAN 无重传机制，网关需要判断命令是否被接收方处理过。
> 节点在 `0x180` 的 `node_state` 里回报最近处理的 `seq`。

### 2.5 故障事件 `0x280`

发送方：bms-node。事件触发，非周期。DLC = 8。

| 起始位 | 长度 | 信号 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 16 | `fault_code` | uint16 | 故障编号 |
| 16 | 8 | `fault_level` | uint8 | 0 提示 / 1 告警 / 2 保护 / 3 严重 |
| 24 | 8 | `occur_count` | uint8 | 同一故障累计出现次数，饱和 255 |
| 32 | 32 | `event_time_s` | uint32 | 相对上电的秒数，小端 |

> 故障事件只在状态迁移时发送，不做周期重复。网关丢失单帧时，
> 靠下一次 `0x200` 里的 `fault_code` 字段恢复当前状态。

## 3. 字节序

- 多字节信号统一**小端**（Intel 格式），与 Cortex-M 原生一致，避免转换开销。
- 例外：UDS 诊断报文内的多字节参数按 ISO 14229 规定使用**大端**。

## 4. UDS 寻址

| 场景 | 请求 ID | 响应 ID |
|---|---|---|
| 物理寻址 | `0x7E0` | `0x7E8` |
| 功能寻址 | `0x7DF` | 多节点响应，需错开延时 |

ISO-TP 参数：

- 标准地址格式，单帧最大 7 字节
- 连续帧间隔 STmin 默认 10 ms
- 块大小 BS = 0，即不分块流控

## 5. 诊断服务

已实现的服务与子功能。未列出的返回 `NRC 0x11`（服务不支持），
不对「没实现」的服务回空数据——那样 tester 会误判成「ECU 正常」。

| 服务 | 名称 | 最低会话 | 需要解锁 |
|---|---|---|---|
| `0x10` | 会话控制 | 默认 | 否 |
| `0x11` | ECU 复位 | 扩展 | 否 |
| `0x14` | 清故障码 | 扩展 | 否 |
| `0x19` | 读故障码 | 默认 | 否 |
| `0x22` | 读数据 | 按 DID 配置 | 按 DID 配置 |
| `0x27` | 安全访问 | 扩展 | — |
| `0x2E` | 写数据 | 扩展 | 是 |
| `0x31` | 例程控制 | 扩展 | 按例程配置 |
| `0x34` | 请求下载 | 编程 | 是 |
| `0x36` | 传输数据 | 编程 | 是 |
| `0x37` | 传输退出 | 编程 | 是 |
| `0x3E` | 会话保持 | 默认 | 否 |

### 5.1 故障码定义

3 字节 DTC，高两位 `11` 表示网络类故障。

| DTC | 名称 | 触发条件 |
|---|---|---|
| `0xC00187` | can bus off | TEC 到 256，控制器退出总线 |
| `0xC00287` | can error passive | TEC > 127 |
| `0xC00387` | can bus stuck | 窗口内反复 Bus Off |
| `0xC10087` | diagnostic response timeout | ISO-TP N_Bs / N_Cr 超时（仅 ecu_server） |

状态位、确认条件、老化规则见 [`architecture.md`](architecture.md) 3.8 节。

### 5.2 0x19 子功能

| 子功能 | 请求 | 正响应 |
|---|---|---|
| `0x01` 按掩码报数量 | `19 01 <mask>` | `59 01 <avail> <format> <count:2>` |
| `0x02` 按掩码报列表 | `19 02 <mask>` | `59 02 <avail> [(dtc:3, status)]...` |
| `0x03` 报快照标识 | `19 03` | `59 03 [(dtc:3, rec)]...` |
| `0x04` 按码读快照 | `19 04 <dtc:3> <rec>` | `59 04 <dtc:3> <status> <rec> <snapshot>` |
| `0x05` 按记录号读 | `19 05 <rec>` | `59 05 <rec> [(dtc:3, status, snapshot)]...` |
| `0x06` 按码读扩展数据 | `19 06 <dtc:3> <rec>` | `59 06 <dtc:3> <status> <rec> <ext:10>` |
| `0x0A` 报支持的码 | `19 0A` | `59 0A <avail> [(dtc:3, status)]...` |

`avail` 是支持的状态位掩码，本实现为 `0xFF`。
`rec` 取 `0x01`（唯一一条记录）或 `0xFF`（全部记录，单条记录时行为相同），
其余返回 `NRC 0x31`。

**`0x03` 与 `0x04` 的关系**：`0x04` 需要 tester 先知道是哪个码，`0x03` 就是
回答「哪些码有快照、记录号是几」的那一步。没有它，tester 只能盲猜记录号，
猜错就吃 `NRC 0x31`。列表为空时回 `59 03`，不下发 NRC——「没有快照」是一个
正常答案，不是错误。

**`0x05` 与 `0x04` 的关系**：入口不同，内容相同。`0x04` 按码查，`0x05` 按记录号查，
用在「不管哪个码，先把 1 号记录都给我」的场景。两者读到同一份快照数据，
这条一致性由互操作测试守住。`0x05` 与 `0x04` 的差别是：没有任何记录时
`0x05` 回 `NRC 0x31`（记录号不存在），而不是空的正响应。

**快照格式**（`DTCSnapshotRecord`）：

```
[DID 个数:1] [DID:2] [数据...]  ×  DID 个数
```

本节点 `DID 0x0001` = 故障发生时的工况，长度随节点不同：
`ecu_server` 为 5 字节（运行时长 4 + 最近一次 ISO-TP 返回码 1），
`node_main` 为 7 字节（健康状态 1 + TEC 1 + Bus Off 累计 2 + 错误等级 1 + 运行秒 2）。

**扩展数据记录 `0x01`**（厂商自定义，固定 10 字节）：

```
发生次数(1) 老化进度(1) 首次发生时刻(4) 最近发生时刻(4)
```

时刻为调用方给的时间基准，单位毫秒，小端，不代表绝对时间。

### 5.3 0x14 清故障码

```
请求：14 <group:3>
正响应：54
```

`group = 0xFFFFFF` 或 `0x000000` 都表示清除全部（本节点没有排放相关故障，
两个值按同一语义处理，避免 tester 发 `000000` 时以为清码失败）。
单条清除传该 DTC 的值。

清码后状态位回到「清码后未测过」，发生次数、时间戳、快照一并清除。

## 7. 机器可读定义

本文件的表格与 [`can_matrix.dbc`](can_matrix.dbc) 一一对应，**以 DBC 为准**。
DBC 已通过 `cantools` 加载与编解码往返验证，可直接用于：

```bash
pip install cantools
python -c "import cantools; db=cantools.database.load_file('docs/can_matrix.dbc'); print(db.messages)"
```

网关端与节点端都应从同一个 DBC 生成解析代码，不要各自手写字节偏移。
